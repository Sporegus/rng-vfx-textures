5. RESPONSIVENESS AND RESOURCE ENGINEERING

First profile the actual application and machine: CPU, RAM, GPU/VRAM when available, runtime framework, model providers, audio path, rendering, and background processes. Choose budgets from measured behavior.

Optimize independently:
- Input responsiveness.
- Speech endpoint/transcription delay.
- Model first-output and total latency.
- Tool action and verification time.
- Rendering smoothness.
- Memory, GPU memory, disk growth, and network usage.

Implement:
- Immediate visible listening/status feedback, without falsely indicating completion.
- Local Stop handling independent of model/network responsiveness.
- Streaming text where supported.
- Bounded asynchronous queues and cancellation propagation.
- Priority for new user interactions over background tasks.
- Event-driven observation, targeted captures, and small necessary context.
- Bounded caches with expiry/invalidation and no reuse of stale targets.
- On-demand loading/unloading of large inactive components, with an idle grace period to avoid reload thrashing.
- Reuse of connections, initialized clients, and safe shared resources.
- Backoff under memory/CPU pressure, with a clear status.
- Limited independent concurrency; exclusive locks for desktop input, audio ownership, and shared mutable project state.
- No perpetual high-frequency screen capture or repeated identical web searches.
- No invisible proliferation of browser tabs, workers, subprocesses, logs, or image buffers.

Preserve master artwork but use appropriate runtime sizes and bounded decoding/frame buffers. Measure visual quality after optimization. A 3000 × 4000 RGBA frame is about 46 MiB decoded; do not assume every master frame belongs in RAM. This is a sizing example, not a claim about the existing renderer.

Use local and cloud components according to configured permissions, hardware, privacy, and budget. A cloud model avoids local model-weight residency but introduces network dependence and usage costs. Benchmark optional smaller/quantized local models for correctness and latency before selecting them.

Create a reproducible benchmark suite:
- At least 30 representative requests covering direct commands, ordinary conversation, ambiguous instructions, project retrieval, research, screen understanding, and longer workflows.
- Measure cold and warm behavior separately.
- Record median and p95 latency with sample counts, hardware/provider details, and variability.
- Compare task success and errors as well as speed.
- Include a repeated-operation/soak test for memory growth and cancellation leaks.
- Retain the baseline and before/after results. Never invent performance numbers.

Target responsive local feedback and interruption; set achievable task-specific latency/memory goals after profiling. Do not promise every task finishes instantly or silently reduce accuracy/permissions to hit a benchmark.
